# Godot 重建：里程碑与版本迭代

状态：迁移计划。Godot 客户端的阶段完成度以对应代码、测试记录和独立审查为准，本文不是完成声明。

用户已决定直接使用 Godot 重做游戏客户端；此前工期作废。不一次性交付“大而全”的替代品，每个版本只解决一个可运行、可测试、可审查的目标。最终方向仍是[架空东方山居绘本 2.5D](design/storybook-valley.md)，不是长期保留几何占位图作为最终美术。

## 经验与工作约束

- **引擎替换不等于画面完成。** UI 外壳、投影算法、占位绘制、最终手绘素材分别验收；一张概念图或一次导入成功不能证明运行画面达标。
- **测试证据必须对应结论。** 类型检查、合成快照、无模型预览、真实 GPU 交互与真实模型长期运行是不同证据，不互相替代。无法执行的检查标为“未验证”，不写“通过”。
- **先贯通一条真实数据路径，再扩展内容。** 客户端不另造世界规则，也不靠装饰补出鱼、库存、人物劳动或房间设施。
- **一个仓库、可恢复的检查点。** 开发、测试和文档仍在本仓库；每阶段留下范围明确的提交和验证记录。保留旧客户端，不把多个临时副本当版本管理。
- **文档随实现变化。** 阶段记录同时列出可用入口、已知缺口、复现命令和回退路径；不以任务清单代替结果。
- **先验证再扩面。** 前一阶段的阻断问题未解决，不把它藏进下一阶段；每次迭代尽量只触及一个运行边界。

## 技术边界

保留 TypeScript 服务的世界模拟、动作判定、路径与位置事实、SQLite 存档、历史记录、模型调度以及 PRIMARY/BACKUP 供应商配置。Godot 负责地图呈现、相机、选择、观察导航和面板，不获得操纵居民或修改世界的入口。

初期直接复用只读 `GET /ai-town/api/world` 完整快照。后续再接入 `/ai-town/api/events` 增量事件协议及历史查询，不把轮询伪称为事件流。快照的世界标识、版本、地图与实体位置必须来自服务端；断线时保留最后已知内容并明确标为旧数据，不自行推进世界。

同一仓库增加 Godot 客户端目录；现有浏览器入口和启动方式在替代验收前保持可用。不会先删除 Phaser/Canvas 实现，也不会迁移正式存档格式来适配渲染器。

已确认开发环境安装 Godot **4.6.3**。安装存在不等于导出可用：导出模板、目标平台产物、图形驱动和浏览器运行必须分别检查。未确认的模板和平台不列入可交付项，不擅自安装依赖。首批以原生客户端为验证入口；Web 发行单独评估，不承诺跨平台完成。

## 分阶段交付

下列版本名称是阶段标识，不改写现有项目版本，也不意味着对应 tag 已创建。通过阶段闸门后再由维护者按仓库约定提交、同步 `bob` 并建立 tag；远程提交与 tag 必须实际核对。

| 阶段 | 范围 | 验收闸门 | 明确不包含 |
| --- | --- | --- | --- |
| **M0：迁移基线** | 保存旧版检查点，确认 Godot、运行入口、API 与渲染边界，记录此计划 | 仓库状态可追溯；不覆盖用户改动；旧版启动方式保留；能说清每个服务的职责 | 完整客户端或美术完成 |
| **M1：最小只读观察版** | 原生 Godot 载入真实 API 快照；2∶1 地形与居民占位；平移、缩放、选择与基础对象信息；连接/错误状态 | 无模型隔离预览接通；无写入请求；非法/失败响应不替换有效世界；重新连接可恢复；投影与选择有自动测试；原生窗口交互另行实测 | 最终绘本素材、室内、全量面板、事件增量、长期稳定性 |
| **M2：空间与更新版** | 建筑占地、门口锚点、前后排序与遮挡；首个共屋真实室内；室内外观察；事件增量与重连基线 | 相同服务状态与旧版位置/人数一致；修订缺口触发重新同步；跨房间、死亡/离开、删除对象和断线不留幽灵；遮挡不隐藏必要选择反馈 | 全部建筑与动作美术、全量档案 |
| **M3：绘本与观察功能版** | 先完成一处共屋、成人与少年素材样板，再逐类扩展；迁移导航、人物/动物档案、关系、历史、跟随、响应式布局 | 按视觉规范实机对照；各类资产脚底/门槛与真实格点吻合；面板开关/重复点击/缩放/窄窗不丢状态；旧版功能覆盖矩阵列明差异 | 未覆盖内容的隐式支持、真实模型长期验收 |
| **M4：候选发布版** | 发布包、部署/导出说明、性能与恢复测试、版本兼容、开源贡献流程 | 固定候选提交；干净检出可复现构建；目标平台实测；独立 review 阻断项关闭；已知问题公开；用户长期运行结果回归后再判定正式发布 | 未测试平台、无限期稳定或生态平衡保证 |

M2 和 M3 都可以再拆小版本。比如先交付“单栋共屋遮挡”，再交付“室内切换”；先交付“两位居民美术样板”，再交付“全体居民”。不会为了一个大版本号等待所有内容一起完成。

## 每次迭代的交付卡

每个阶段在实现/审查记录中回答：

1. 本次目标、实际改变与明确未覆盖的内容。
2. 对应本地提交；同步后记录远程 `bob` 提交和 tag（未同步就写未同步）。
3. 精确测试命令、结果、测试数据来源；是否运行窗口/GPU/触控验证。
4. 独立审查发现的问题、修复与复测；未解决项是否阻断下一阶段。
5. 新旧入口与回退方法；下一阶段的最小目标。

代码存在、测试通过、review 通过、远程同步是四种不同状态，不能合写成一个“已完成”。

## 数据安全、验证与回退

开发验证使用项目已有隔离预览或明确标注的合成夹具；不读取 `.env`、密钥、真实存档，不发真实模型请求。凭据和正式数据库保持在服务端，不打包进 Godot 项目。开发缓存、导出产物、日志和本地配置由 `.gitignore` 排除；推送前检查待提交清单。

已有预览命令为 `npm run dev`，只读 API 位于 `http://127.0.0.1:3413/ai-town/api/world`。它新建临时数据库、禁用模型且不推进时钟。因此接通它能证明协议与呈现路径，**不能证明自主行为、持续世界更新或长期运行**。Godot 的具体运行/测试命令随 M1 实现记录，不能先写未存在的命令。

长期运行由用户执行。候选版本应提供明确的运行条件、观测指标、日志位置与停止/恢复方法；开发侧负责可重复的短程故障与回归检查，不把用户尚未提供的长期结果填成通过。

任何阶段失败，先恢复使用保留的旧客户端观察同一服务；不为回退修改或重置正式数据库。检查点回退必须保护阶段之后的用户改动，不能用破坏性重置代替问题定位。只有 Godot 的功能覆盖、视觉与发布验证达到替代门槛后，才单独提出旧客户端退出计划。
