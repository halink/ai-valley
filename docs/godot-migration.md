# Godot Web：从最小山谷逐步长大

## 最新方向

新版**只做浏览器版**，不交付原生桌面游戏，不考虑移动端。使用 Godot 真 3D 和手绘风格材质；Godot 编辑器和 headless 是开发工具。此前把原生窗口作为交付目标的选择已纠正，不能继续作为验收条件。此前三天工期已作废。

先交付一个小而完整的可行版本，再基于它增加功能和地图，直到自主生活山谷的最终目标。不要以搬迁旧客户端全部面板或补齐整个旧功能清单作为第一版门槛。用户概念图和设计资料保留为参考，新视觉不必严格沿用旧 2D/2.5D 提案。

## MVP-0 最小闭环

约 32×24 的小地图、两位居民、一处共屋、食物与水源。需求影响决策；行动要经过真实路径、现场耗时和资源/库存/需求结算；观察者能看懂采集、进食、饮水、休息及失败，而不是看预设动画假装完成行为。

当前 Web 工程入口先用显式标示的规则驱动，临时内存世界，不读 `.env`、不调用模型、不保存世界。Web release 已实际导出，并有隔离 HTTP、规则和 headless 证据；**浏览器真实画面与交互尚未验收，因此 MVP-0 尚不能认定已完成**。连接另一执行会话的 loopback 服务被拒绝是当前验证限制，不能以导出成功掩盖。

## 小版本路线与退出条件

| 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| MVP-0：浏览器生活闭环 | 小地图、两居民、食水与共屋，真 3D 手绘风格；规则驱动清晰标识 | 浏览器可加载、连接真实后台快照；生活行动结算可复现；中文、选择/缩放、室内外、刷新/断连与视觉检查通过；独立 review 和文档一致。 |
| MVP-1：自主生活与保存 | 在同一小地图接入显式 PRIMARY/BACKUP、失败/等待反馈、保存和恢复 | 浏览器同源持久入口可用；真实模型短程证据另列；旧状态恢复、未决请求和重试不重复结算；密钥只在服务端。 |
| MVP-2：视觉深化 | 在 MVP-0 的手绘风格上精修材质、居民、建筑和动作可读性 | 实际浏览器/GPU 性能与美术检查通过，不以概念图或 headless 结果替代。 |
| 后续逐版扩展 | 每次一种玩法或一块区域，如工具伐木、河流钓鱼、耕种、社交、住房、动物生态 | 先定义增量价值，再提供规则、画面、回归及保存兼容证据；不一次承诺大而全。 |
| 发布候选 | 整合已验证的小版本、部署和操作文档 | 干净检出可复现；浏览器与后台部署验证；独立 review 无阻断；用户长期结果回归后再判定正式版本。 |

这些名称是路线标签，不代表 tag 已建立或阶段已完成。后续顺序可依实际反馈调整，不恢复固定工期。

## 已有工程与未完成项

已有小世界行动结算、需求和库存、移动轨迹、共屋双床与室内观察、基础姿态、中文 UI、手绘风格材质。独立持久服务和主/备用模型配置属于可复用工程，不等同于已经通过浏览器/真实模型验收。

当前规则 Web 服务仅监听本机 `127.0.0.1:3414`。持久 Web 的实际浏览器验收、公开 HTTPS 部署、访问控制和真实模型验收仍需完成。持久服务的锁目前依赖 Linux；Linux 后台可以服务其他平台的浏览器，不能把 Mac 本地存档支持当成浏览器交付前提。

## 清理与交付纪律

- 删除与新展示方向无关的旧客户端、实验资源和入口；先查依赖并保留可恢复版本，不清扫实际存档或秘密。
- 保留当前仍复用的模拟、存档、模型和测试契约，以及用户设计资料；旧功能存在不代表当前 MVP 已实现它。
- 所有开发与测试在同一仓库。小提交、独立 review、文档与测试同步；核实远程 SHA 后才能说 push 成功。
- 密钥、数据库、运行日志、缓存与导出结果不入库。阶段 tag 对应实际验证范围。
- 分别报告代码完成、Web 导出、HTTP/规则短测、浏览器/GPU、真实模型和长期运行，不混用证据。
- 长期运行验证由项目所有者负责；开发侧仍需短程回归、故障恢复和独立审查。

运行方式见 [Web MVP](godot-web-mvp.md)；贡献流程见[贡献指南](../CONTRIBUTING.md)。
