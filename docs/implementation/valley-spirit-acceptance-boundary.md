## 先补齐三项独立输入

1. **G2 类型政策及部署信任根。** 由部署方按角色独立固定签审人、轮换及撤销规则，并正式批准单类型的量、时效、冷却和原子记账政策。用实际原档证据复核，不从申请、开发签章或环境变量引入信任根。当前[部署信任干演练](dry-deployment-trust.md)即使匹配也固定返回 `liveAuthorized:false`。
2. **独立的普通档新建登记与防回档水位。** 由可信部署方在首建前预留身份；登记源需在同一存档备份／恢复域之外维护代数、最新头和实际消费记录，并在不一致时拒绝写入。当前[新建注册证据合同](ordinary-fresh-enrollment-evidence.md)只校验测试登记源、且只接受显式零消费，**不注册真正普通档**。现阶段只考虑新建档，不接管、回填或迁移既有玩家档，也不把开发 V3 拷入普通运行。
3. **供应商原始授权和对账证据。** 明确允许向哪个端点、为哪个运行发送哪些数据；匹配真实账户，核对上一未知请求处置、实际用量／账单及当期零价材料。[材料校验](production-model-source-custody.md)和[本机托管](production-model-held-supervisor.md)只验证离线签审一致性和本机进程结果，不证明真正供应商身份、成本或已获准发送。凭据不交给本页、不进仓库或测试产物。

## 分工与放行顺序

- **开发**：先把已具备的本地链路接至上述受控边界并保持默认关闭。用同一提交级别的单元测试和短验证记录真结果及负例，优先检查撤权、确切到期、重开不重扣／未知不重发、错档、账本残缺、授权关闭后世界仍能推进。只提交源码和文档，不提交本地测试、存档、账、凭据或签名材料。
- **部署授权人**：核查上述独立输入及范围，未满足就不启用真实供应商或普通 G2。批准也不替代开发验证。
- **用户／测试组**：G0、G1、G2 全部实现且开发侧快速验证通过后，再提交对应版本、可重现步骤、预期与未验证边界；详细场景、真实玩法长时运行和验收由用户／测试组执行。局部开发档、离线替身、签审干演练和无界面解析均不能当作提测或正式验收。
