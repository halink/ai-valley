# 本人未完食物加工信息

## 问题与范围

原行业加工菜单只说明新配方的原料和总工时，不说明本人原批次已经投入的劳动、现留原料与产出数量。`gameMeal` 的真实配方是1生猎肉、1清水、1木材，累计35分钟实际劳动后产出2餐食；原菜单未区分已经劳动10分钟和29分钟。它不是基础 `cook` 的2根菜、1水、1餐食。

本次为本人已知、当前可观察且有使用权的食物加工批次提供独立决策摘要，同时区分新开工与续作菜单。没有修改任何配方、工时、食品营养、腐败规则、自动选择或自动劳动，也没有扩大菜单预算或保证加工选项每轮出现。

## 事实与边界

- 只读取引擎实际会继续的第一个本人 `working` 批次，要求已知建筑、现有公共/所有者/住户/合法租用权，并通过现有 `canInspectBuilding` 现场观察边界。另一个人的批次、远处项目、隔着另一建筑的项目和已撤销使用权项目不进入新摘要。
- 使用批次内保存的原配方，不用当前新版本覆盖原料、产出和总工时。已经劳动、剩余实际劳动、原配方投入、原批次现留原料分别列出。剩余劳动不包含行走、室内移动、等待和中断；不把完成时点当作承诺。
- 新开工明确从本人随身库存投入材料，完工才获得产出；续作明确材料已在原批次，不是重复开工成本。原料不足、权限变化、工位冲突和腐败仍由现有执行规则重验。
- 独立摘要不随普通菜单裁剪而消失，不进入可截断的家庭长记录。只保留一个当前批次，每个物料清单最多展开8种，多余种类明确计数；不泄露原始食品批次账本。
- 生猎肉是不能直接进食的加工原料，餐食等现有规则允许的食品可直接进食。这个规则不证明实际库存新鲜，未完成产出不计为已有口粮，不推算未来成品的保质期或营养。没有新增批次，也不补造历史时效。
- 缺失或非法的实际劳动、原料/产出记录保留为未知，不填成0，不重建库存。摘要是独立快照，要求主体与游戏分钟匹配；反复生成不改变世界。

## 两项必要的执行保护

1. 原来菜单的只读验证遇到缺少 `definition` 的旧批次时，会通过 `actionRecipe → bindRecipeSnapshot` 写入定义。现在只读路径只计算同一个版本标识，不写世界；真实执行仍按原迁移规则绑定快照。旧配方即使已从当前可用列表撤下，也能继续自己的有效原批次。
2. 新续作菜单绑定现有 `batchId`。执行前以及实际工作时，如果该批次已完成、取消、消失或被另一批次替代，必须重新决定，不能用迟到的续作选择偷偷扣新材料开新批次。同一已完成动作的既有幂等保护保持原顺序。未提供 `batchId` 的既有正常开工路径仍可按原规则创建批次。

这两项只防止读取时写状态和旧选择换目标，不改变劳动速度、产出量、腐败时钟或居民的自主选择。

## 真实决策输入对照

主测试在 `createFrontierWorld(5401)` 的**显式合成库存**中，经最终编号菜单、`parseChoice → submitPlan → stepWorld` 工作10分钟。只改这个合成批次的实际劳动记录到29分钟，其余本人库存和同一游戏分钟保持相同，最终 `prepareModelDecision` 输入分别包含：

```text
已实际劳动10分钟 / 总需35分钟；尚需25分钟实际劳动
按原批次配方完工产出2份餐食，尚未入库

已实际劳动29分钟 / 总需35分钟；尚需6分钟实际劳动
按原批次配方完工产出2份餐食，尚未入库
```

删除本次摘要与加工选项后，两个context一致。另一路完全由正常编号选择完成10分钟开工、10分钟等待、内存SQLite保存/重载、19分钟续作、最后6分钟劳动，核对只扣一次输入、总计35分钟、只产2餐食。这里的选择由离线脚本指定，不是真实模型行为或自然九人粮食链证据。
