# 现场浆果余量进入最终决策输入

## 可复现缺陷与修复范围

在 `b2552ac` 的正常个人决策流程中，`decisionContext.resources` 已按本人知识、位置和视线带入浆果当前余量，但最终模型消息只通过采集选项间接展示信息。两条先红反例证明：

- 现场看见 **0 份与 0.5 份**，因为均不足一整份，没有采集项，最终菜单和消息完全相同。
- 现场看见 **3 份与 12 份**，因为单次采集上限为三份，最终菜单和消息也完全相同。

这是已有个人观察被最终输入丢掉的问题，不是权限、采集量或资源生成缺陷。两条红测使用配对的合成状态检查输入表达，未改变默认世界的资源；修复也不增加食物。

新增 `visibleBerryObservationNote` 从**现有 context 快照**投影最多四处现场浆果的位置和当前余量，明确零份、不足一整份与未知。段落独立于家庭综合记录，先保留当前采集菜单的目标，再按距离和 ID 排序；超量明确未展开，不表示别处没有食物。

它不读全局世界、旧地址库存、再生时间、容量或未来产量。离开后没有远程刷新，也不把未采浆果计入已有口粮。可见但隔水或隔墙不能接触的地点仍只是观察，采集必须继续走原菜单和执行校验。不新增动作、不改变菜单编号、路径、数量、危险优先级、居民自主选择或 v4 控制器。

新增输入有成本：这批归档中 7261 次决策多了一段，最长 537 UTF-8 字节（另有分隔换行）。四处上限会省略部分观察；紧张时家庭综合记录先让出预算。完整编号菜单和观察仍超硬上限则保持报错，不静默删除动作或放松限制。

## 与苏葵旧轨迹的关系

对 `bf1a7769` 的完整默认十五日合成归档 `output/test-tmp/nine-menu-stress-RKKaPI/` 重新核查：

- 苏葵有 1224 次选择，其中 218 次**提示中四舍五入后的饥饿值至少 80**。这不是连续饥饿分钟，也不与身体判定器的浮点阈值混用。
- 这 218 次中，196 次有现场浆果观察，180 次所见浆果点全部为零。比如决策 5744、分钟 15996，现场两个地点 `(419,232)` 和 `(427,232)` 都是零，但这些当前数量没有进入原提示。
- 25 次有进食或现场采果选项，20 次选择吃或采，五次按旧脚本优先撤离危险。正式直接采果机会遗漏到最终菜单的次数为零。
- 69 次不可达目标失败全部来自探索。记忆食源访问有三次被野猪打断，四次采集因完成时资源/位置变化失败。不能把这些直接叫作菜单或寻路错误。

以上支持“存在与缺食情境有关的信息遗漏”，**不证明它导致了苏葵的长期饥饿**。旧 v4 读取结构化 context 和编号选项，本来就不读取新增的提示文字。不能声称补文字以后这个脚本会更聪明，也不能将下面的同动作对照包装成真实 AI 收益。

独立资源路径审计也没有找到需要修复的食源可达性缺陷：300 个随机小地图上，使用逐边可通行 BFS 对照 2400 条食源路径和 600 组菜单，全部匹配，覆盖围栏、合法入口和断连。随机检查不是穷尽证明。三组既有专项 33/33 通过；本轮因此没有改导航或食源选择规则。

## 三层验证

### 先红后绿与独立边界

主测试四项、[独立审查](../reviews/visible-berry-observation.md)六项，连同原食源 33 项和赠粮提示 17 项合跑 **60/60 通过，零跳过**。覆盖：

- 上述相同菜单、不同实际观察的提示区分，三种模型均核对。
- 不认识、室内、远方、遮挡不泄露；未知/非有限/负量不补成零。
- 四条上限、当前采集目标优先、稳定排序、缺少目标不补造地点。
- 无再生内部字段，旧快照不查询世界，世界/context 不变。
- 可见但不可达仍不新增采集项，提示预算保留与硬超限拒绝。
- 两个同种子克隆分别在真实采集/进食中持续准备提示或不准备，实际世界与收据完全相同：原地点扣三份，另选吃一份后本人剩两份，进食营养 12；准备提示不会代选、产粮或进食。

### 十五日归档输入重放

`replay-inputs.mjs` 顺序读取原归档 8042 条 selected 记录，仅使用各条原个人 context、菜单和回复：

1. 当前生成的全部菜单与原菜单逐项相等。
2. 原回复重新解析出的动作与原选择相等。
3. 删除唯一新增的现场观察段落后，8042 个原 prompt 哈希全部精确恢复。
4. 所有输入 context 读取前后完全相同。7261 条有新观察，其余原消息不变。

这是**个人输入重放，不推进世界**。不将旧世界的最终健康、饥饿或实际供食结果冒充新世界结果，也不据此声称 v4 重新作出了 8042 次自主选择。

### 新的一日世界核对

当前代码实际新跑一次默认 seed 5401、原 v4、分钟 480→1920 的九人世界，目录 `output/test-tmp/nine-menu-stress-uWSiTp/`。初始世界与控制器哈希和旧十五日归档一致；将这一日与旧归档同一时间前缀比较：

- 509 次选择及动作轨迹相同，只有 483 个 prompt 哈希改变。
- 1441 个实际引擎子步的九人身体及八供餐渠道字段完全相同，包含原分享过程的 .25/.75 子步。
- 午夜落盘快照、个人库存和其中的资源记录完全相同。

旧轨迹中在 1920 之后才完成的动作，比较时明确保留为新一日终点的“仍在途”，不把未来完成带回截止点，也不将原记录缺失字段补为零。

首次比较把新内存 report（含 `roomAt:undefined`）与旧落盘 JSON（不存储该字段）直接比，出现表示形式差异。保留原失败日志后，改为双方读取各自落盘 report；`--recheck` 仅复核同一次新运行，未修改世界产物或重新跑世界。修正后所有比较通过。

**这一日对照没有覆盖旧轨迹后期高饥饿时段，也不是新的十五日验收。** 原十五日长期标准仍失败；本轮只修复可验证的信息投影，不承诺饥饿、赠粮或生存改善。

### 提交前独立补验与字节成本

在 Linux / Node 24.22.1、清空继承环境和原离线守卫下重新运行同组 **60/60**，全仓类型检查及隔离服务端编译也通过。额外从 `b2552ac95dd7d9ef54b672827dc3712a10351ad1` 取出原提示构造函数，分别以三种模型格式复现两组信息折叠，并确认当前版本在菜单不变时区分观察。

对同一批 8042 份历史个人 context 分别使用三种模型格式重投影，全部没有触发硬上限，也没有因本次新增段落额外裁剪家庭记录。GLM 与 DeepSeek 格式的最大完整序列化输入均为 19169 字节，Qwen 为 19355 字节；相对原构造器，单次序列化增量最多 539 字节（包含 JSON 转义后的分隔换行），每种格式合计增加 3270476 字节。最紧的 DeepSeek 40,000 字节限制仍至少剩 20831 字节。537 字节是单段观察的归档最大值，不是所有可能输入的普遍上限。

这些数值只是应用侧序列化字节，不是模型 token、费用或提供方实际接受的保证。三种格式共用同一批原 GLM 脚本输入，不代表三条不同模型轨迹。更大的家事记录仍可能被优先裁剪，任意过大 context 仍可能报错。
