# 雇佣加工批次与签约配方隔离

## 已复现的缺陷

真实合成 `open → post → apply → select → accept → work` 流程中，店铺只有 2 根菜、2 水，根菜于工作第 2 分钟过期。原实现仍在 40 分钟工作后产出 2 餐，并将已签约配方改成 `turnip: 0`。原因是 `batch.inventory` 与 `contract.recipe.input` 为同一对象，腐败扣除实物也减少了后续校验用的需求量。批次的输出与配方输出同样共用引用。

这里使用显式合成库存、隔离世界和内存 SQLite，不读取真实存档，不调用模型或浏览器；不是九人自然开局或真实长期验收。

## 修复边界

- 新批次独立复制投入与产出。旧的内存别名在食品容器登记和雇佣初始化时拆开，保持当时实际数量，不补发已丢物品。
- 已绑定的历史配方定义是原聘约证据，保留其投入、产出、技能、工位与时间。正常初始化可用它恢复被污染的可变配方，绝不使用当前激活版本改写已签约约定。
- 缺少合同绑定时，只有相同招聘 ID、雇主、店铺和条款的招聘快照可作为恢复证据。没有这条证据时，结构完整且投入均为正数的旧快照沿用原内容再绑定。完全没有配方快照的早期旧档沿用既有迁移规则，但明确取原始 v1，行业岗位也不追随当前激活版本。
- 已有绑定但找不到或无法验证其定义时，不从当前版本猜测。缺少可信证据的归零投入，包括旧初始化已把污染快照绑定成 legacy 定义的情况，均停止加工；不补材料、不继续计薪。退出/解雇及实际余料、未挣工资的退款仍可进行。
- 对投入中原本含冗余零量字段的合法自定义配方，同样保守停工，不擅自删除字段来改约；本次不声称能区分这种情况与已被旧逻辑污染的快照。
- 食品推进和工作入口都检查未完成批次的实际投入、约定输出、耗时与有限非负进度。缺料、额外未约定原料或加工记录不符不能继续完成，现有退料路径只转回当时仍在批次里的实物。食品交易保留其原到期时间与营养定义。

不会改动合同工资、期限、本人工作意愿或已经计入的劳动。坏批次不会把劳动进度转给新批次。若同一已提交工作时段内商店仍备有完整原料，原有雇佣语义允许另开一批，但从零进度开始；没有余料则失败，后续轮次仍必须重新取得原配方要求的实物。

## 旧数据能与不能修复的部分

恢复承诺不等于恢复实物。若旧档曾产生错误成品，当前修复不会追溯扣回可能已转移或消费的成品，也不会补造根菜；缺少账本证据无法安全重建这段历史。若所有独立历史证据都已丢失，输入字段被删除或正数已被减少，单凭剩余有效快照无法证明原始约定，不能声称对所有损坏旧档完整恢复。可检测的归零、缺失定义和不完整批次会阻断继续生产。

## 离线验证

主回归 `tests/employment-conservation.test.ts` 经真实引擎执行开店、招聘各步骤与本人工作，覆盖：

- 修复前 6 条回归 2 通过、4 失败，包含 40 分钟腐败产餐、引用别名、污染旧档和缺料完成入口；修复后全部通过。
- 腐败/无腐败，工作中 SQLite 重载，绑定后当前配方更新，后续轮次仍需原料。
- 正常完成与完成重放，足额材料只产出相应成品，配方和总货币保持不变。
- 已污染旧快照仅修配方、不补批次；已满进度但缺料的批次不能产出或再计薪。
- 一批腐败后使用第二批新料必须重新工作；同批幸存水果退回后仍保留原批次时效。
- 每个实际食品容器逐物品核对批次数量，无悬空容器账目。
