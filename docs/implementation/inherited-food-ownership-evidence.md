# 继承导致现有食品库存归属变化的有限证据

本切片仅观察成功 `production.inherit` 对现有食品实物的实际 `ownerId` 改写。它独立于 `foodTransfers`，不是物理搬运、食品生产、加工投入、进食或腐败，也不构成完整所有权或食物账。

## 记录范围与时点

每次成功登记一个份额产生一条 `foodOwnershipChanges` 回执，含原继承对象、实际份额、继承人、完成时点、真实事件和可知计划 ID。`stocks` 中逐个保留真实容器、容器类型、改写前的实际所有者和改写后的所有者：

- `estate-stock`：实际封存包中的现存可食食品。根遗产拆包的真实 ID 可为 `estate:…:share:…`，不会为了名称统一重命名容器。
- `orchard-stock`：未砍果树当时已有的 `fruit`。
- `animal-stock`：动物当时已有的 `egg`、`duckEgg` 或 `milk`。不计动物本体、羊毛、未生成产品。

不计 `share.inventory` 摘要、公共累计余额、田地或未收获作物、温室床、房屋、工具、钱款。零食品的合法继承可以留下 `stocks: []`，证明已观察该次继承，而非创造食品数量。

回调只在原有真实赋值行、且所有者确实变化时读取实物数量。`acceptEstateParcels` 可以命中仍在祖先遗产列表中的后继包，因此不能从 `personId`、容器名称或所在遗产列表推断 `fromOwnerId`。初始化、分份、未接受份额的后继分拆本身不产生回执；实际领取 `collectEstate` 是另一个物理事务，不重复计归属变化。

## 批次和不确定性

数量来自改权瞬间的物理库存，不来自开步或末步差额。有限非负实物值可证明正数数量；无效、非数据属性或无法识别的数量保持 `null`。同对象别名、重复容器 ID 等冲突使相关数量未知；相同 ID 的冲突记录合并为一个未知容器，不双计。`ambiguous` 标记别名/所有者身份不确定性，不能据此输出肯定跨界量。

所有 `lots` 与 `nutrition` 均为 `null`，即使此刻能够找到批次。原因包括：

1. `prepareShares` 已建立新包实物，但其原批次须等外层 `foodTransaction` 的 `finally` 才沿原路由交付。
2. 旧库存的批次可能曾由初始化修补，现有元数据不能独立证明原始来源。
3. 继承时刻、包创建时刻、当前营养定义和饥饿变化均不能补造原批次证明。

本切片不调用 `foodContainers`、初始化或修补来获取证明，不改写世界/存档格式、居民知识、权限或原有继承结果。

## 同一分钟的顺序

实际引擎先腐败扣减，再完成居民继承，之后行业自然生成。测试以树上原有4果为例：先腐败1果，归属变化记录3果，随后自然新增另有原生成回执。不能把末步水果数当继承量。

九人 helper 对旧 `foodLosses`/`foodFlows` 仍沿原端点归属规则处理；同分钟端点所有者跨边界时保持 `unknown`。本次没有用末步所有者回填同分钟腐败或增长回执，也没有新增通用事件顺序账，因此这些端点不能声称闭合。

## 可选采集、发布与严格验证

- 新覆盖标记为 `foodOwnershipCoverage: 'production_inherit_existing_food_v1'`。旧文件未带这组新字段，或保留合法回执却缺覆盖标记时，该切片覆盖未知，不补零或历史记录；有覆盖标记却无数组是无效证据。旧 `foodTransferCoverage` 含义不变。
- 状态仅存一次同步观察的外部捕获结构。普通 `stepWorld` 不采集；预测副本即使 world ID 相同也不串入原世界。
- 运行时仍仅在 SQLite durable commit 和成功安装世界之后发布冻结副本。数据库失败、revision 竞争或抛异常草稿不得发布；恢复成功一次，重载不重播。
- schema 拒绝多余字段、访问器、自定义原型、稀疏数组、非有限值、非法容器/食品、重复容器/食品、无改权及伪造营养批次。一个事件只能有一个份额回执，所有容器放在同一 `stocks` 数组。
- 实际继承事件与 `(estatePersonId, shareId)` 均去重；日报和九人累加器在整步验证后才改变游标、覆盖或汇总。旧日报已有缺测/历史流事实保持兼容，不因本切片补造证明。
- evidence writer 保留独立切片和哈希链。失败或遭篡改封存的顶层及嵌套归属总量均为 `null`。

## 日报与固定九人边界

`createIsolationEvidence` 增加独立的归属明细、已观察/缺测分钟及部分数量总计。`auditFoodOwnershipChanges` 与按日分组提供独立审核，`fullOwnershipLedger: false`。

九人 helper 使用最初固定九个 ID 加 `commons`，不随生死、在地/外出或居民状态变化。每个实物按回执实际 `fromOwnerId`、`toOwnerId` 计算：

- 外部→九人/公共：`scopeInflowTotals` 归属流入。
- 九人/公共→外部：`scopeOutflowTotals` 归属流出。
- 内部→内部与外部→外部：保留事实，跨界量为零。
- 冲突/缺失所有者或数量：受影响方向与品项保持未知，不当作零。

归属量不加到物理转移、来源新增、加工或九人摄入。完整 `foodProduction`、`foodConsumption` 仍为 `null`，`completeFoodLedger: false`。汇总数量表示被观察到改权的既有食品份数，不是可食供应能力或完整收支。
