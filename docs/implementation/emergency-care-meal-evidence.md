# 儿童紧急供餐的可选证据

## 真实范围与不变的权限

默认关闭的 `directEatingEvidence` 现在增加独立可选 `emergencyCareMeals`，仅记录真实完成的 `emergencyCare.feed` 与 `emergencyCare.rescueMeal`。`tendChild`、普通 `care`、长期照护、公共服务、旅途、自主进食和食品来源/加工仍分别列账。新增切片不是完整供餐覆盖或完整食物消费账本，`foodProduction`、`foodConsumption` 仍未知。

先对照 `src/world/emergency-care.ts` 的实际规则，而非由事件文字、约定或库存差反推吃过饭：

- 当次 `rescueMeal` 需要成年人自行决定，健康高于30、体力至少10；孩子未成年、严重衰弱（健康不高于20）、饥饿至少12、不能自主决定/表达或未满六岁，未明确拒绝，双方在合法可接触现场，且没有在场能及时决定的监护人。它不建立连续约定。
- 有限 `feed` 先由提供者提出、独立成年复核人亲自核验监护缺口；六岁以上且有决定与表达能力的孩子另行接受。幼儿没有伪造的接受记录。约定自提出起固定24小时、最多四餐，不提供自动工作或储粮预留，每餐仍由提供者重新选择。
- 两条供餐路径均耗时20游戏分钟，完成时重新核验权限、位置、拒绝、能力、需要和实际库存。优先一份个人 `meal`，否则一份个人 `turnip`，另扣一份个人 `water`；不使用桶水、公款、公共食品或孩子的财物。
- 实际饥饿减量来自原 `foodValue`，最低截断到0，不是 `tendChild` 固定48。原定义缺失时引擎保留既有物品定义回退；证据不会把回退值或实际饥饿缓解冒称已知的原批次营养。

本次未改变以上规则、世界、存档字段、居民知识、菜单、授权或食物初始化行为。提议、复核、接受、探望、撤回、帮助告示、事件及约定内既有回执均不是新增摄入记录。

## 成功点的事实

扣减前只读实际选中的原批次，成功扣减并生成原供餐事件后记录：

- `action: 'emergencyCare'`、具体 `operation`、完成分钟、原事件、原计划和活动定义。
- 提供者、受益孩子与唯一来源 `person:<providerId>`。
- 实际 `meal` 或 `turnip` 与个人 `water` 各1单位的扣减。水的营养为0、食品批次为空，不与食物混计。
- 按原事务先到期顺序取用的原批次数量、生产/到期时间、原定义、可知营养。缺批次、缺定义或同次捕获中修补的来源保持未知，不初始化批次、不回退到当前食品营养、不用饥饿差倒推。
- 动作前后的 `hungerBefore`、`hungerAfter` 和实际 `hungerRelief`；之后同一步代谢不混入本次供餐。
- 限期供餐保留真实 `agreementId` 与本次1至4的 `mealNumber`；当次救急两个字段均为 `null`，不制造连续权限。

批次修补标记仅存在于单次捕获，不能证明前次捕获或重载前的历史来源。没有将它当作跨存档批次真实性机制。

## 提交、未知与一致性

捕获器只挂在当前 World 的 WeakMap，作用域结束后 `finally` 清理，不进入序列化世界或模型输入。预测副本不向真实世界捕获器发布。同步失败没有返回成功观察；捕获器不是世界回滚器，原运行时草稿和存储事务仍负责实际回滚。

运行时仅在 `WorldStore.commit` 成功、已安装提交世界之后发布。世界提交失败不发布草稿餐食，重试只记录真实成功一次。writer 或观察器失败不撤销已提交世界，但封存不全时顶层和 `directEating.emergencyCareMeals` 完整总量均为 `null`。

schema-1 旧记录没有新字段仍可读取：缺字段为未观测，显式 `[]` 才是该步观测零。零步、缺开始/结束边界、漏步、非递增revision、重复事件、损坏或缺封存均不能证明完整新增总量。旧切片独立保留，不能借新字段补全整个消费账本。

严格 schema 对每层对象和数组白名单复制，拒绝额外字段、访问器、符号、数组空洞和非有限数，并核对：来源人和受益人不同、个人容器、两种固定材料各1、供餐模式与协议编号、有效原批次数量/时间/营养、饥饿需求和实际差值。已知原营养须与截断后的饥饿变化一致；未知原营养只保留真实变化。协议内重复/跳号、换提供者/孩子、时间倒退、同约已观测餐次跨度达到24小时及跨切片事件重复使总量未知。单条记录没有协议提出时间，不能仅凭它独立证明期限或授权；真实完成点仍按原规则核验。会话可从协议第二、三或四餐开始，不补造历史餐次。此处是受信任内部证据一致性检查，不是外部真实性签名或独立重演授权。

逐日切片保留原始 receipts、已观测/未观测分钟和总量。当日任何分钟缺测则总量保持未知，后续零次不能修复。区间为 `(fromMinute,toMinute]`，午夜完成归刚结束的一天；分数分钟按实际完成时点分组，不制造无观测日期。
