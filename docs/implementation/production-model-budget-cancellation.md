# 未派发取消与模型额度的原子结算

## 观察与归因边界

`bob 62e3c39` 的 GitHub CI run `43039374075` 脱敏诊断显示：前两段累计完成16、28次请求，第三段实际请求为0，actorMask为0，但有20次tick并推进约24.16游戏分钟。两账无pending，runtime没有失败且已封存；最终由原观察验证器拒绝 `observation_count`。它不是启动或监督器超时失败。

这些工件没有保存前两段的取消计数或usageWindow，因此不能据其汇总直接宣称原CI的确切预算状态。下面的源码缺陷及确定性复现与该计数形状高度吻合，不是原CI现场状态重演。

## 已证实的缺陷

runtime先为模型请求预留保守输入/输出额度，再将本地请求开始及usageWindow持久提交。如果提交跨过准入截止，已有取消流程会正确拒绝调用模型和transport，并保存取消回执，但原代码没有释放这笔已知未派发的预留。

SQLite重开后，ModelBudget把尚未完成的记录按可能已计费的中断请求保留。两次取消可以留下约3.3万保守额度，加下一次请求的预留就超过45,000 TPM。调度器因预算不足每秒推迟provider，没有新增transport、attempt或错误；世界时间仍可推进，最终也可干净封存。它不表示九名居民仍忙于15分钟停留。

保留的修前确定性probe使用原默认九人、真实runtime、内存HTTP、双账和新SQLite，只将测试时钟在前两段本地开始提交后移到cutoff，并使用固定400ms合成调度成本。结果为：

- 三段实际请求16、12、0，累计完成16、28、28，取消次数1、1、0。
- 三段均正常封存，第三段推进28.8游戏分钟，九人都已ready且lastError为空。
- 保留预算33,509，加恢复时最小新预留12,375，共45,884，超过未改动的45,000限制。
- 第一份无该固定调度成本的probe只有一次取消，结果16、11、18；保留其未达假设的结果，不将它伪装为复现成功。

上述数字是本地合成数据，不是供应商token用量或费用证明。正式回归在修前另行失败于“third segment requests: 0”，红灯保留在 `output/no-request-epoch-diagnosis/regression-red.tap`。

## 最小修复与不变量

`ModelBudget.prepareUnsentCancellation`只接受当前预算内部的原始、未完成reservation对象。相同内容的副本、已经完成、已经移除或重开前取得的对象均被拒绝；其他历史或并行预留保持不变。

runtime只在原有显式取消分支调用它：本地开始已经持久化，当前代次仍存活，准入明确关闭且处于排空，并且注入模型从未被调用。`modelInvoked`在调用模型之前立即置为true，因此同步模型异常也不能被当成未派发取消。

操作分两阶段：

1. 先生成去除这一个预留的独立usageWindow快照，不改变内存预算。
2. 该快照与原取消回执写入同一个世界事务。durable commit成功后、通知订阅者前，才从内存预算移除该对象。

事务失败时内存和磁盘都保留原预留，不能发布取消或干净封存。后续观察器出错仍按已有路径失败关闭，不因预算释放变为成功。已调用模型、已派发、结果未知、transport错误、无效响应、普通停止和抛错都不能进入这个释放路径。旧合成run的预算及源码契约不被回填修补。

本修复不减少本地开始、双账attempt或启动预留，不重置累计次数，不清空预算，不调整TPM/RPM、时钟、并发、截止、重试或fallback。原每段至少9请求、九人覆盖、完整双账对应与截止验证保持原样。它不是退款，也不证明供应商实际费用为零。
