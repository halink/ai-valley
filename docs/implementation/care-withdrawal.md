# 一次基础照护的本人撤回

## 已复现的缺口

普通 `care` 提议被本人接受后成为 `accepted`，但旧菜单只列 `open`，旧 `respond` 执行也先要求 `open`。受助者因此失去正常停止入口；施助者已排队的喂食仍能执行。旧 `care` 动作只带对象身份，还可能在执行时误用后来另一份同意。

本切片保留提议、接受、实际照护三步，只补齐本人有效停止与原授权绑定。没有增加成人紧急照护权限，天气调度仍默认关闭。

## 当前规则

- 最终居民菜单保留属于本人的、未过期且尚未完成的一次照护停止项；焦点、普通菜单预算、船上、家庭同行及医疗乘员筛选不能裁掉它。受助者不必走向施助者，也不要求施助者此时清醒、有决定能力或在场。
- 受助者仍可表达时，可仅停止本人原来的照护。没有完整决定能力不再阻断这个窄停止，但不会授予接受新照护、安排别人、进食、移动、修改财产或其他决定能力。正在执行自己的其他计划时，也只提供停止和短暂不表示停止，不覆盖其原计划。
- 一个有效停止必须是单独提交的行动。身份、提议种类、状态、有效期、表达能力、演员版本和字段形状均重新验证；与其他行动混装则整份拒绝。
- `submitPlan` 接到有效停止即把这一提议置为 `declined`，不安排三分钟工作或走路。已经选好照护的施助者在下一次移动/工作推进前失败，完成函数也独立复验，因此最后四分之一分钟和居民遍历顺序不会造成额外消费。
- 正常照护菜单的 `care` 动作携带具体 `proposalId`。执行要求提议仍为 `care`、施助者和受助者完全相同、仍被接受且未过期。旧提议失效后不改用另一提议、监护或紧急权限。确有另一份独立接受的照护时，必须另选绑定那份提议的行动。
- 未绑定的旧普通照护计划/活动不会在读取存档或执行时补造同意；如果当前有普通同意，须重新决定。既有监护和紧急照护入口仍使用原条件，且不能用来绕过这位受助者对该施助者当前提议的有效停止。
- 拒绝只处理这一提议，不写永久或全局的 `refusesCare`，不撤销另一份明确同意，不改变决定能力或监护身份。已经真实完成的单次照护仍是历史事实，不能退回物资、倒转身体变化或重新履行。
- 远处施助者不会因一次停止直接得到记忆或通知；事件仅按既有现场见证规则传播。停止的权限效力与他人是否当场听见分开处理。

普通停止与长期照护本人停止共用有限的菜单、调度和即时提交入口；长期合约的来源退款及别名边界见相应长期照护文档。非 care 的已接受婚恋、生育提议不使用这个停止入口。

## 存档与兼容

沿用原提议的 `open/accepted/declined/expired` 状态；实际单次履行后仍置为 `expired`。新增动作字段 `proposalId` 不从库存、观察记录、亲属关系、后来提议或模型文字回填。内存 SQLite 重载保持原身份、拒绝和履行状态；旧未绑定活动保守失败而不扣物资。普通 `society` 测试也改为显式引用本人原来接受的提议。
