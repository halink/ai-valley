# 请求终态与重启计量

## 已确认的问题

旧运行时在结果提交后才删除内存请求槽，但没有在同一次持久提交中删除 `metrics.inFlight`。九位居民的假模型请求全部成功后，立即正常停机并重开 SQLite，仍可能把列表中的已成功居民再次计作“未完成请求，用量未知”。成功提交后的订阅者异常还可能把同一个结果再计为模型失败。

## 本次范围

- 成功响应，包括被当前世界拒绝的迟到或不适用计划，在提交结果、计数和预算快照的同一 world 事务中，只清除当前居民的待回记录。
- 普通模型失败在持久记录已知 token 或一次未知用量、保留原保守预算时，结束对应本地待回状态。未知仍为未知，不是退款、零费用证明或远程请求结束证明。
- 只有存储提交返回成功后，请求才标记为已持久终态。在订阅者执行期间重入 tick、启动另一请求或停止，不会把该请求重新写为待回，也不会再次计为中断。
- 已持久成功后的订阅者异常不再二次计量模型结果。普通运行时保留异常传播；受控验收仍按原规则失败关闭。
- 真正尚未返回、提交未成功、停止后晚到的请求继续使用原保守处理。旧存档中无法证明完成的历史 `inFlight` 不凭聚合成功计数猜测或自动修正。

本次不修改模型预算退款、未派发取消回执、准入控制、价格授权、生产 journal ACK 或重试授权。world、session、journal 不是一个跨库事务；world 已提交但 journal checkpoint/ACK 尚未完成，仍依原桥接规则阻断恢复，不因本地待回列表变空而放行。正式入口的真实模型开关保持未接通。

## 验证

`tests/runtime-request-recovery.test.ts` 的 8 项专用回归先在旧实现中出现 6 项红灯，再通过修复：

1. 正式 seed5401 九人全部成功，立即正常停机及 SQLite 重开。
2. 两个并发请求只完成一个，另一个停止并晚到，只保留一次真实中断。
3. 已知 token 的 `DecisionError` 终态与预算。
4. 未知用量失败保留保守预算，重开不重复计数。
5. 成功提交后订阅者抛错，不增加第二次模型失败。
6. SQLite 触发器阻止终态事务，结果、待回与预算一起回滚。
7. 独立子进程在结果事务之前退出，重开保留一次未知中断。
8. 独立子进程在结果事务之后、请求清理之前退出，重开不产生假中断。

独立审查见[请求恢复审查](../reviews/runtime-request-recovery.md)。均使用内存或仓库临时目录中的合成 SQLite 与假模型，不读取真实存档或密钥，不代表真实模型费用与长期生产验收。

独立四项反例另覆盖订阅者重入 tick 与第三请求开始、受控异常停表，以及一次性结果写失败后原失败记账事务成功的情况。最后一项保留原错误处理：已有一次持久 unknown 账目便不在重启重复计数，预算条目仍保留；本次没有重新设计存储异常的重试策略。
