# 直接进食与烹饪候选独立审查

## 结论与实现边界

此次审查针对 `direct-food-choices.ts`、基础32项菜单和 `focusedChoices` 的组合，不将此前工作区其他未提交修改算作此次修复。未发现本次候选保留方案的阻断问题。

- 全部本人可食物品先按稳定物品表轮换为最多4项，再进入基础菜单，避免固定尾项永久丢失。当前目录有20种可食物品。
- 基础烹饪排在最多4项进食之后；外层从已有 cook 候选按稳定ID轮换保留1项，包括已经验证的借用厨房候选。外层不得再次裁掉本轮4项进食。
- 最终普通菜单上限59：原56项、最多2项水源、最多1项烹饪。实时停止入口继续按原规则额外恢复，故59不是带任意数量停止入口的绝对上限。
- 替换只允许多余目标反思，不应以删除紧急、拒绝、停止、水源或进食入口支付新候选位置。
- 公平性限于候选集合稳定且覆盖连续30分钟窗口；任意时刻抽样、库存持续变化或居民始终不决策不构成必然覆盖。菜单可见不等于选择、可达、成功完成或生存保证。

## 独立回归

`tests/direct-food-choices-review.test.ts` 共9项：

1. 160项合成工作议程与全部关注方向下，连续20窗口覆盖所有本人食品，保留烹饪，菜单编号唯一且上下文不被构造过程改写。
2. 当前真实世界时点的正常编号菜单与prompt中选择目录末尾鱼干，解析后通过 submitPlan/stepWorld 完成一次进食，扣本人1份且有饥饿缓解。
3. 编号选择烹饪实际消耗2根菜和1水、产1餐食，但不自动吃掉产物。
4. 选择后材料不足或厨房使用权被撤回时，实际引擎失败，不制造餐食或营养。
5. 食品在进食过程到期，实际引擎失败且没有营养缓解。
6. 本人批次未知时不补造批次；改变他人私有库存和批次不改变完整决策prompt。
7. 12岁不能烹饪、4岁不能直接自食；照护表达专用、撤离表达专用、乘员及家庭旅途限制不被新保留槽绕过。
8. 9个厨房候选在3种关注下连续9窗口各出现一次，同时保留合成紧急口粮和即时停止入口。此项检查候选选择，不宣称这些合成厨房具有实际执行权限。
9. 半份餐食、1根菜、无水不会产生虚构完整餐食或烹饪候选，也不自动提交行动。

测试fixture是 `createWorld(5401)` 后显式改为formal并配置库存和时点的合成世界，不是自然正式九人开局。执行用例基于与世界分钟一致的当下context；纯轮换用例只改变合成context时点，不声称经过真实时间演化。fixture先调用一次context初始化已有定义，然后检测后续候选构造的状态不变性。
